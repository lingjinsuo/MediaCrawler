### 1.3 设计原则

| 原则 | 说明 | 落地方式 |
| --- | --- | --- |
| **分层解耦** | 采集、存储、识别、展现四层单向依赖，上层不反向调用下层 | `media_platform` → `store` → `api` 三段式单向流 |
| **平台可插拔** | 新增平台不改动框架代码 | `AbstractCrawler` / `AbstractStore` 抽象基类 + 工厂注册 |
| **配置驱动** | 行为差异全部外置到配置，避免硬编码分支 | `config/` 目录集中管理 |
| **优雅降级** | 外部依赖（平台接口、LLM、浏览器）异常时不中断整体链路 | 空 dict 返回 + 重试 + 状态标记 |
| **单向数据流** | 平台原始数据 → 统一模型 → 存储 → 识别 → 线索，全程可追溯 | `model/` 统一字段定义 |
| **配置即代码** | 变更走 Git 评审，禁止直接改生产环境 | Git Flow + MR 流程 |

### 2.2 分层职责与依赖约束

| 层级 | 包路径 | 职责 | 允许依赖 | 禁止依赖 |
| --- | --- | --- | --- | --- |
| 展现层 | `api/webui/` | 页面渲染、交互、图表 | 无（纯静态 + fetch） | 后端 Python 模块 |
| 接口层 | `api/` | 参数校验、编排、业务聚合 | 采集层（经 subprocess）、存储层（经 DB）、识别层 | 直接操作爬虫内部对象 |
| 采集层 | `media_platform/`, `base/`, `tools/`, `proxy/` | 登录、请求、解析、翻页 | 存储层（写数据）、`config/` | `api/`（严禁反向依赖） |
| 存储层 | `store/`, `database/` | 持久化、去重、模型定义 | `config/`、`model/` | `api/`、`media_platform/` |
| 识别层 | `sql/`, `tools/llm_client.py` | 意图判定、线索生成 | 存储层 | 采集层 |

> **强制约束**：`media_platform/*` 与 `store/*` 中不得出现 `import api` 或对 FastAPI 的任何引用。评审时作为红线检查。

### 2.4 关键设计决策（ADR 摘要）

| 编号 | 决策 | 背景 | 取舍与代价 |
| --- | --- | --- | --- |
| ADR-1 | 采集任务以 **subprocess 隔离**运行，而非同进程 asyncio | 爬虫依赖浏览器上下文，异常会污染 Web 服务进程 | 牺牲少量启动开销（约 1s），换取服务稳定性；日志经 stdout 捕获回传 |
| ADR-2 | Web 控制台采用 **iframe + 静态页**，不引入 SPA 构建链 | 页面间共享登录态与数据上下文，避免框架引入的工程复杂度 | 页面独立发布，需手工维护 5 个 HTML；已规划 T-8.6 前端工程化改造 |
| ADR-3 | 购买意图识别采用 **关键词匹配**为主，LLM 为辅 | 关键词命中精准、可解释、成本为零；LLM 存在延迟与误判 | 召回率受限（漏判语义表达）；T-8.4 接入 LLM 兜底 |
| ADR-4 | 线索池使用 **独立表** `comment_push` 而非在评论表加标记 | 线索有独立生命周期（待处理/已处理）、独立查询维度 | 数据冗余（评论内容存两份），换来线索检索性能与工单闭环能力 |
| ADR-5 | 统一以 **秒** 为时间戳单位入库 | 各平台原生单位不一（XHS 毫秒 / DY 秒） | 需在写入前统一转换（`normalize_timestamp_to_seconds`）；历史数据需洗数 |
| ADR-6 | 敏感配置经 **环境变量**注入，`.env` 不入库 | 当前 Cookie 已泄漏至 Git 历史（T-7.1 待修复） | 本地开发需自备 `.env`；换来凭据可轮换、可审计 |

### 2.5 核心数据流

**采集主链路**

```
控制台点击「启动」
   → POST /api/crawler/start  (Pydantic 校验参数)
   → crawler_manager.start()  组装命令行 → subprocess.Popen
   → main.py (子进程)  cmd_arg 解析 → CrawlerFactory.create_crawler()
   → crawler.start()  登录态准备 → 浏览器/CDP 启动
   → search()/detail()/creator()  遍历目标
   → client.request()  签名 + 代理 + 重试
   → extractor 解析 → store 写入 (MySQL)
   → stdout 实时输出  ──►  crawler_manager._read_output()
   → _simplify_progress_log() 精简  →  LogEntry 队列
   → WebSocket /ws/logs 广播  →  控制台实时日志面板
```

**识别主链路**

```
调度器 9:00-20:00 每小时触发 (或手动 POST /api/comment-push/run-batch)
   → CommentAnalysisBatch.run(platform)
   → 从 mc_setting.comment_key 读取词库（每次跑批读一次，批量缓存）
   → 查询各平台评论表 WHERE analysis_status = 0 LIMIT 500
   → 逐条判定：
        ① 评论时间 < 3天前  → analysis_status=1，跳过
        ② 命中关键词        → analysis_status=2 + 写入 comment_push
        ③ 未命中            → analysis_status=1
   → session.commit()  整体事务提交
```

### 3.2 采集层：风控对抗设计（抖音 Argus 专项）

#### 3.2.1 问题定义

抖音于 2026-08 起在网关层引入 `ArgusSecurityPlugin`，请求缺少合法签名时被拦截，典型响应：

| 响应特征 | 含义 |
| --- | --- |
| `""`（空 body） | 签名校验失败，body 被清空 |
| `"blocked"` | 明确的风控拦截 |
| `"Blocked by ArgusSecurityPlugin"` | 插件拦截标识 |
| `"Uifid Not Found"` | 缺少设备指纹 uifid |

#### 3.2.2 处理策略（四层防御）

```
第 1 层  预防  CRAWLER_MAX_SLEEP_SEC = 5   降低请求频率
         DISABLE_SSL_VERIFY = False         SSL 校验失败会触发 ArgusSecurityPlugin
         ENABLE_CDP_MODE = True             复用真实浏览器 Cookie 与指纹

第 2 层  识别  client.request()  四类特征匹配判定为风控拦截
         → 不抛异常，标记 is_argus_blocked

第 3 层  重试  指数退避 3s → 6s → 12s（最多 3 次）
         每次重试前 _refresh_cookies_from_browser_safe()
         从 playwright_page.context 重新提取 Cookie 并更新 self.headers

第 4 层  降级  重试耗尽 → 返回空 dict（不抛 DataFetchError）
         上层据空数据优雅退出，不中断整条链路
```

#### 3.2.3 关键实现约定

```python
# client.request() 核心骨架（media_platform/douyin/client.py）
max_retries = 3
retry_delays = [3, 6, 12]          # 指数退避

for attempt in range(max_retries + 1):
    try:
        response = await client.request(...)
        if _is_argus_blocked(response.text):
            if attempt < max_retries:
                await self._refresh_cookies_from_browser_safe()
                await asyncio.sleep(retry_delays[min(attempt, len(retry_delays)-1)])
                continue
            return {}                 # 降级：返回空数据而非抛错
        return response.json()
    except DataFetchError:
        raise                         # 主动抛出的直接上抛
    except Exception as e:
        last_error = e
        if attempt < max_retries:
            await self._refresh_cookies_from_browser_safe()
            await asyncio.sleep(retry_delays[...])
            continue
        raise DataFetchError(f"{last_error}, {last_response_text[:200]}")
```

**三条硬性约定**

1. **返回空 dict 而非抛异常**：上层翻页逻辑依赖 dict 判空，抛异常会击穿整个采集链路。
2. **Cookie 刷新必须静默失败**：`_refresh_cookies_from_browser_safe` 内部 `try/except` 吞掉异常，仅记 warning。浏览器已关闭时刷新必然失败，不应因此升级为致命错误。
3. **page 健康检查前置**：每次请求前访问 `self.playwright_page.url` 做探活，异常则置 `None`，避免长跑场景下 page 被其他标签页切走后整链失败。

#### 3.2.4 翻页死循环防护

`get_all_user_aweme_posts()` 三重保护（对应测试 `tests/test_douyin_argus_fallback.py`）：

| 保护 | 触发条件 | 行为 |
| --- | --- | --- |
| 空页保护 | 连续 2 页返回空 dict | 停止翻页，保留已采集结果 |
| 游标停滞保护 | `max_cursor` 与上一轮相同 | 停止翻页（否则无限循环） |
| 类型保护 | 返回 `None` / 非 dict | 安全返回空列表，不抛 `TypeError` |

### 3.3 存储层设计

#### 3.3.1 多后端抽象

```
store/{平台}/_store_impl.py
   ├── DbStoreImplement      → MySQL/PG（异步 ORM，含去重）
   ├── SqliteStoreImplement  → SQLite
   ├── MongoDbStoreImplement → MongoDB
```

#### 3.3.2 存储设计要点

| 要点 | 实现 | 关联需求 |
| --- | --- | --- |
| 字段截断 | 写入前按 DB 列长截断（标题 500 字符等），防 MySQL 截断报错 | F-2.6 |
| 时间统一 | `normalize_timestamp_to_seconds()`：≥10¹² 视为毫秒除以 1000 | ADR-5 |
| 去重 | 按平台唯一键（note_id / aweme_id / video_id + comment_id）判重 | F-2.2 |
| 引擎复用 | `database/db_session.py` 用 `_engines` 字典缓存引擎，避免重复建连 | F-2.8 |
| 事务边界 | `get_session()` 上下文管理器：正常 commit，异常 rollback 并重抛 | — |

#### 3.3.3 数据模型

**`mc_setting` 约定键值**

| key | content 格式 | 用途 |
| --- | --- | --- |
| `comment_key` | 逗号/顿号/分号/换行分隔的关键词 | 购买意图判定词库 |
| `crawl_presets` | JSON 数组 | 一键抓取预设方案列表 |

### 3.4 识别层设计：购买意图判定

#### 3.4.1 判定流程

```
输入：评论内容 content、词库 keywords（来自 mc_setting.comment_key）
  │
  ├─ ① 时间闸门：comment_time < now - 3天
  │     └─→ analysis_status=1，返回「评论已超过3天，跳过入库」
  │
  ├─ ② 关键词命中：_match_keywords(content, keywords)
  │     ├─ 命中 → analysis_status=2 + 写入 comment_push(hit_keyword=命中词)
  │     │        返回「命中关键词: {kw}」
  │     └─ 未命中 → analysis_status=1
  │                  返回「未命中关键词」/「未配置 comment_key，默认无意图」
  │
  └─ ③（待实现 T-8.4）关键词未命中时可选走 LLM 语义判定
```

#### 3.4.2 关键词词库解析

```python
# sql/comment_analysis_batch.py
def _split_keywords(raw: str) -> List[str]:
    """支持半角逗号、全角逗号、顿号、换行、分号作为分隔符；
    自动 trim、去前后引号、去空项、去重(大小写不敏感)。"""
    parts = re.split(r"[,，、\n;；]+", str(raw))
    ...

def _match_keywords(content, keywords) -> Optional[str]:
    """子串包含匹配，大小写不敏感；
    命中则返回第一个命中的关键词(原文大小写)，否则返回 None。"""
    content_lower = str(content).lower()
    for kw in keywords:
        if kw and kw.lower() in content_lower:
            return kw
    return None
```

**设计约定**

| 约定 | 说明 |
| --- | --- |
| 词库读取时机 | 每次 `process_platform` 开始时读一次并缓存，避免逐条评论查库（性能关键） |
| 匹配方式 | 子串包含，非分词。召回优先于精度——电商评论口语化，分词成本高收益低 |
| 大小写 | 不敏感，英文关键词（如 "vip"）同样生效 |
| 未配置词库 | 返回空列表，所有评论判为无意图，**不报错**（降级） |
| 命中记录 | `hit_keyword` 存原始大小写的首个命中词，供前端做关键词效果分析 |

#### 3.4.3 线索生成与工单状态

```
comment_push.push_status:  0 = 待处理    1 = 已处理
comment_push.process_content : 处理备注（运营填写）
comment_push.process_time    : 处理时间
```

线索生成时自动置位规则：**评论时间超过 3 天 → 直接 `push_status=1`**（历史线索无需跟进）。

#### 3.4.4 调度器设计

```python
# api/main.py::run_batch_scheduler
启动 → 计算到下一个整点的秒数 → sleep
循环：
    9 <= hour < 20  → await batch.run()
    否则             → 跳过
    await asyncio.sleep(3600)
```

| 设计点 | 说明 |
| --- | --- |
| 启动即对齐整点 | 避免服务重启后立即触发一次跑批 |
| 异常隔离 | 单次跑批异常仅打印日志，不终止调度循环 |
| 生命周期绑定 | 通过 FastAPI `lifespan` 管理启停，关闭时 `task.cancel()` |
| 手动触发 | `POST /api/comment-push/run-batch?platform=xhs` 可随时执行 |

```
评论表 analysis_status 流转：

  [0 未分析]
```

### 6.2 Python 编码规范

| 项 | 规范 |
| --- | --- |
| 编码 | UTF-8，文件头保留原 License 声明 |
| 行宽 | 100 字符（ruff 默认 88 可放宽） |
| 命名 | 模块/函数/变量 `snake_case`；类 `PascalCase`；常量 `UPPER_SNAKE_CASE` |
| 类型标注 | 公共函数与接口必须标注类型；内部函数可省略 |
| 异步 | 所有 IO 操作必须 `async`；禁止在 async 函数内调用阻塞 IO（如 `requests`） |
| 日志 | 用 `utils.logger`（统一 logger），**禁止裸 `print()`**（`main.py` 入口的编排输出除外） |
| 异常 | 自定义异常继承 `DataFetchError`（`media_platform/*/exception.py`）；捕获时区分「可重试」与「致命」 |
| 魔法值 | 常量提取到模块级或 `config/`，禁止散落数字 |
| 注释 | 复杂逻辑必须写「为什么」而非「做了什么」；TODO 必须带负责人与日期 |

**异步与阻塞的边界（重点）**

```python
# 禁止：在 async 函数中直接执行阻塞子进程
proc = subprocess.run([...])              # ❌ 阻塞事件循环

# 正确：交给线程池
proc = await asyncio.get_running_loop().run_in_executor(
    None, lambda: subprocess.run([...])
)                                          # ✅

# 正确：异步子进程
proc = await asyncio.create_subprocess_exec(
    *[...], stdout=subprocess.PIPE, stderr=subprocess.PIPE
)                                          # ✅
```

### 6.3 异常处理规范

```python
# ✅ 平台层：可预期的业务异常用自定义异常
raise DataFetchError(f"{e}, {response.text}")

# ✅ 识别层：单条失败不中断批次
try:
    await self._process_comment_with_keywords(...)
except Exception as e:
    print(f"[{cfg['name']}] 分析 -> 失败: {e}")   # 跑批脚本内允许 print

# ✅ 接口层：转为 HTTP 异常
except Exception as e:
    raise HTTPException(status_code=500, detail=f"跑批执行失败: {str(e)}")

# ❌ 禁止：吞掉异常
except Exception:
    pass                                        # 静默失败，无法排查
```

**分层异常策略**

| 层 | 策略 |
| --- | --- |
| 采集层 | 单个请求失败重试；重试耗尽抛 `DataFetchError` 或返回空 dict（按场景约定） |
| 存储层 | 单条写入失败记录日志后继续；批量事务失败整体 rollback |
| 识别层 | 单条评论失败跳过并计数，不中断整批 |
| 接口层 | 统一转 `HTTPException`，文案面向运营可读 |

### 7.1 T-7.2 接口鉴权设计

**方案**：JWT 无状态鉴权 + 角色权限。

```

      → 校验 mc_user 表（新增）或环境变量账号

      → 角色不足 → 403

```

## 9. 附录

### 9.1 术语表

| 术语 | 含义 |
| --- | --- |
| 线索 / Push | 命中购买意图关键词的评论记录，存于 `comment_push` 表 |
| 命中关键词 | 触发线索的词库词，存于 `hit_keyword` 字段 |
| 跑批 / Batch | 定时或手工批量处理评论、生成线索的任务 |
| 预设 / Preset | 一套固定的采集参数配置，存于 `mc_setting.crawl_presets` |
| 风控 / Argus | 抖音平台的请求签名校验与反爬机制 |
| CDP 模式 | 通过 Chrome DevTools Protocol 接管本机真实浏览器 |
| uifid | 抖音设备指纹标识，缺失会触发 `Uifid Not Found` |
| 脱敏 / 匿名化 | 对昵称、用户 ID 等个人信息做掩码或哈希处理 |
| 词库 | `mc_setting.comment_key` 中维护的购买意图关键词集合 |
